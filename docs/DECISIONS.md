# KontrolPR technical decisions

## Incremental PR reads — 2026-10-23

The user approved optimizing repeated PR reads without a shared credential or a new PR backend. Keep existing local IndexedDB/session boundaries, 12-hour retention, logout cleanup, ten-minute visible polling, permissions and QA/developer state semantics. Do not silently retain private repository data across new logins. No dependencies or UI changes required.

`reader.ts` accepts an optional repository checkpoint and emits its replacement only after all listing/detail work succeeds. It contains version, repository, read-start cursor, last-full timestamp, QA signature and exact PR IDs. First/legacy reads use full listing; compatible later reads filter `updated_on` across OPEN/MERGED/DECLINED with a two-minute overlap. Using read-start rather than completion time avoids skipping updates during long reads. Follow every `next`, deduplicate by ID/newest timestamp, merge deltas with cached snapshots and prune finalized records beyond 30 days. Partial listing responses retain all normalized fields and `next`; unchanged detail reuse additionally checks source/destination hashes. Existing concurrency bounds remain two repositories and three PR groups each.

One-hour reconciliation is a conservative repair mechanism: the next due check after that interval does full inventory and detail reading, removing missing PR and detecting comment edits/deletions, approvals or commits not signaled by the listing timestamp. Do not claim the provider guarantees that every such event changes `updated_on`; unannounced changes may remain stale until reconciliation. Normal signaled changes are handled by the next successful poll. Invalid/incompatible checkpoint, wrong inventory/scope/QA signature, clock rollback or explicit force also requires full reading. Incremental-list 400 falls back to full reads; network/auth/rate-limit failures preserve the old checkpoint, not fake empty success.

The monitor stages repository checkpoints/statistics until the active session/generation is verified. Failed repositories retain their old cursors, denied repositories lose them, and successful repositories update independently. Checkpoints are stored atomically in the existing snapshot envelope. Loading validates version, exact inventory, repository ownership and login/sync time bounds independently of PR content; invalid metadata falls back safely without discarding valid cached PR. F5 preserves cursor and polling schedule; logout, expiry or repository removal clears applicable state. Statistics count actual calls, listed summaries, refreshed detail groups, reused cached PR and removed records; no logs or credentials are added.

Provider references checked 2026-10-23: [PR listing and repeated state filters](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-pullrequests/#api-repositories-workspace-repo-slug-pullrequests-get), [filtering and sorting](https://developer.atlassian.com/cloud/bitbucket/rest/intro/#filtering), [partial responses](https://developer.atlassian.com/cloud/bitbucket/rest/intro/#partial-responses). These document query/projection capabilities, not an exhaustive event-delivery guarantee.

Authority is the verified Bitbucket UUID in `server/initial-qa-team.ts`, never the selected perspective, display name, email or client payload. Every request verifies Basic credentials against the fixed Bitbucket `/2.0/user` URL with no redirects, bounded response/body size and timeouts. Tokens are transient and are never logged or persisted server-side. Any valid Bitbucket identity can read this roster; this is deliberately not a workspace ACL. PR/repository access remains checked directly by Bitbucket.

One fixed private Vercel Blob object stores only versioned members, timestamp and verified editor UUID. Server-only `BLOB_READ_WRITE_TOKEN` is required; no browser Blob SDK, public storage, ephemeral in-memory production fallback or fake success. Missing configuration returns 503. An absent object in a configured store supplies the confirmed initial Javier/Diego/Iván roster until the first edit persists it. Empty stored membership remains empty. Reads bypass Blob caching; atomic first creation and ETag `ifMatch` updates reject simultaneous stale writes with 409. Responses are private/no-store and auth requests bypass the PWA cache.

Client membership always overrides old personal QA preferences. It is checked at login, F5, manual/due sync and explicit refresh. Initial failure pauses classification; later failure preserves the last verified roster with warning. Writes are pessimistic, duplicate-protected and revision-conditional, with no automatic write retry after uncertain completion. Conflict refreshes the server list before the editor reviews/retries. Logout/session replacement invalidates late replies. Initial roster/editor policy stays server-only, not in the public JS bundle. Existing 12-hour browser credential persistence remains its previously accepted risk; this does not implement HttpOnly login or instant push.

SDK dependency: `@vercel/blob` 2.8.2 (Node >=20) is server-only and necessary for private reads and conditional writes; no Vercel CLI/runtime package added. Local dev/preview adapts Node requests into the same Web Request handler. Deployment requires one user-created private Blob store and the complete Vercel project, with production and preview storage isolated. No resource creation/deployment performed by this implementation. Official references checked 2026-10-23: [Blob SDK](https://vercel.com/docs/vercel-blob/using-blob-sdk), [consistent private reads](https://vercel.com/changelog/vercel-blob-now-supports-consistent-reads-on-private-storage), [Node Web Request functions](https://vercel.com/docs/functions/runtimes/node-js).

## Bitbucket Cloud integration

The integration boundary uses the official Bitbucket Cloud REST API base `https://api.bitbucket.org/2.0` and the documented resource paths for pull requests, commits, comments, activity and diffstat.

The OAuth consumer documentation states that authorization-code exchange uses client authentication with a key and secret, while browser-only implicit grant returns an access token in the URL fragment. Atlassian's current API documentation also notes a 2026 requirement for OAuth requests to use the API host and Bearer headers, and the implicit flow is not a safe long-term choice for this product. KontrolPR therefore ships with an explicit demo mode and an `AuthProvider` abstraction. A production integration needs a supported Atlassian integration or a small confidential backend that exchanges authorization codes and keeps refresh tokens server-side. No OAuth secret is stored in `VITE_*`, source, public assets or the production bundle.

The relevant official references reviewed on 2026-10-22 are:

- https://support.atlassian.com/bitbucket-cloud/docs/use-oauth-on-bitbucket-cloud
- https://developer.atlassian.com/cloud/bitbucket/rest/intro/
- https://developer.atlassian.com/cloud/bitbucket/rest/api-group-pullrequests/
- https://developer.atlassian.com/cloud/bitbucket/rest/api-group-commits/

## Review-state model

The raw Bitbucket state (`OPEN`, `MERGED`, `DECLINED`) and properties (`draft`, `queued`) are preserved. The internal QA flow is computed from normalized events and effective-code fingerprints. A title or description change is metadata only. A commit hash change is not enough to require another QA pass; the normalized diff fingerprint must change after relevant QA feedback.

The app remains conservative when evidence is incomplete. It will not infer approval from an arbitrary comment, and it does not claim unresolved conversation counts unless the API data supports that calculation.

### Reload-persistent session until Santiago midnight (superseded)

The 2026-10-22 follow-up explicitly requests persistence across F5 and logout at midnight. In this frontend-only app, the approved implementation stores the email and scoped token in localStorage with a fixed expiry at the next `America/Santiago` calendar-date boundary. Revalidation on reload never renews that deadline. The boundary is calculated through the timezone calendar, not a fixed UTC offset or a rolling 24-hour duration; Chilean DST days can be 23 or 25 hours. Storage denial falls back to memory with a visible warning.

This tradeoff exposes the credential to same-origin JavaScript. No client-side encryption or HttpOnly protection is claimed; a confidential backend would be required to remove the token from browser-readable storage. The login UI discloses retention. Expiry/rejection removes stored credentials and live data, aborts session requests and requires reconnection without injecting demo fixtures. Expired credentials are purged at next startup when the browser was closed; this app cannot physically delete storage while not running. Explicit disconnect removes the credential locally, not the Atlassian token. Other tabs observe session changes through storage events. Preferences remain isolated by verified account identity.

The create-token action now links directly to https://id.atlassian.com/manage-profile/security/api-tokens . The scoped-token steps and 1–365-day provider expiry follow https://support.atlassian.com/bitbucket-cloud/docs/create-an-api-token/ and https://support.atlassian.com/atlassian-account/docs/manage-api-tokens-for-your-atlassian-account/ . Provider-token expiry is independent of the shorter KontrolPR session deadline.

Repository configuration and exclusions are now editable in the UI, partitioned by verified identity. A repository-scoped exclusion is different from an individual PR exclusion. Discovery is based on actual PR authors and comment participants, not an invented complete repository member list.

The live reader is an incremental integration, not completion of the original code-evidence requirements. Historical effective content comparison, version-associated approvals and robust offline live-data caching remain pending and are identified in the product. A source hash or diffstat alone does not prove reviewed content equivalence. Notifications currently report new remote events without claiming that a commit necessarily changed effective code.

Notifications use browser permission, a PR-grouped unread center and a Web Audio chime unlocked by user action. One sync emits at most one aggregate system notice and one chime. No push service is introduced; a suspended browser cannot promise scheduled checks. Full remote comment text remains available in PR detail only, with pre-wrapped line breaks and long-word wrapping.

Preferences and observed event IDs belong to the current browser installation. IndexedDB is the intended persistence layer, with an in-memory fallback for environments that do not expose IndexedDB. Local “ignore developer” and “ignore PR” settings never modify Bitbucket and are not shared between users or devices.

## PWA update behavior

The audit found an unterminated notificationclick block in the original public service worker, a constant version unrelated to app builds, and automatic activation. These are replaced with a build-generated worker whose content hash covers the worker template and emitted bundle. Installation precaches the matching HTML/CSS/JS shell but does not call skipWaiting. A persistent update banner offers the waiting version; its explicit action checks for the newest worker, waits for installation, then requests activation. Controller changes reload existing controlled tabs once; initial installation does not reload. Other open KontrolPR tabs also reload when the shared worker activates. Failures and activation timeouts allow retry without deleting account data.

The app checks for updates on startup, once per visible minute and on eligible visibility/online events. Navigation requests bypass the HTTP cache; offline navigation falls back only to this worker's matching shell. Non-navigation API/unknown/authenticated requests never receive an HTML fallback. Cleanup deletes only obsolete kontrolpr-static-* caches, never unrelated caches, IndexedDB or localStorage. Vercel headers revalidate HTML, bypass SW cache and retain immutable hashed assets. This follows the [service worker lifecycle](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers), [updateViaCache contract](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/updateViaCache) and [Vercel headers configuration](https://vercel.com/docs/project-configuration/vercel-json). No script can literally send Ctrl+F5 to browser chrome; versioned assets, uncached navigation and controlled activation implement the intended update behavior.

## Session-scoped PR cache and measured loading

The user now explicitly requests reusing loaded PR on F5. A versioned, runtime-validated snapshot in IndexedDB contains PR, comments, commits, repository scope and last-sync metadata, but no credential. Its account ID, original login creation/expiry and exact repository set must match before restoration. Revalidation of Bitbucket identity still precedes any private cached UI. A new login does not reuse another login's snapshot. The existing session deadline remains unchanged and logout/expiry clears the snapshot; if the browser is closed, expiration is enforced and cleanup attempted on the next startup. Local browser storage is browser-readable, not encrypted or server-backed. Storage denial falls back to memory with an honest reload warning. Build updates preserve compatible snapshot data.

A fresh snapshot defers repository synchronization until ten minutes after its original last completed sync. A stale snapshot remains readable during refresh, and manual sync ignores freshness. Resuming a tab checks the deadline rather than syncing unconditionally. Repository changes trigger a scoped refresh. A 403 discards denied repository data; transient errors keep previous data with a warning. Offline identity verification still blocks private cached UI. Permission revocation can remain invisible until the next repository check, at most the freshness window while active.

Progress is based on real pagination and completed PR work, with an indeterminate phase while the total is unknown. Bounded parallelism reads two repositories and three PR groups per repository (each comments/commits pair may run together). Cached unchanged details count as processed without refetching. The summary disclaimer is removed as requested; this does not implement historical content comparison or approval ingestion. The quality/role audit records those remaining limitations.

The real reader now fetches individual PR participants and paginated activity in addition to comments/commits. It reconstructs source/destination revisions from update events and associates QA feedback/approval timestamps with those revisions only when the available history is complete. Current participant approval is required to avoid retaining revoked approvals; self-approval is excluded. Identical immutable heads prove the same content. Otherwise, SHA-256 fingerprints compare validated net patches with object-index hashes removed, retaining paths, modes and hunk locations. Same edits at shifted hunk locations remain inconclusive. Binary, oversized (>2 MiB), invalid UTF-8 or malformed/incomplete diffs are not evidence. Immutable fingerprints are cached; absent review references do not trigger diff downloads. Effective QA IDs participate in evidence-cache validity.

The [official commit API](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-commits/) specifies source-first `source..destination` and `topic=true` for source-to-merge-base comparison (unlike Git CLI order). We call that repository endpoint directly because [PR diff endpoints](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-pullrequests/) redirect and this credential-bearing client deliberately rejects redirects. Current read scopes suffice; no mutation endpoints are added. HTTP 401/403 still propagate to the access-removal flow. Other comparison failures remain unknown. Patch grammar alone cannot detect a response cut off at a complete file boundary: independent paginated diffstat for the same immutable pair must therefore agree on file count and added/removed line totals, with no duplicate paths. Statistics are a coverage check, never the content fingerprint itself. Evidence format 2 invalidates older unvalidated fingerprints and refreshes old cached evidence. Validation with real PRs remains a release requirement.

State precedence is finalized > current active approval after feedback > verified changed content > later commits with inconclusive comparison > QA feedback/author response > new. Inconclusive post-review commits use `COMMITS_PENDING`, owned by QA and explicitly not an effective-fix claim. Approval only describes the observed reviewed content, never functional correctness. This supersedes the earlier reader limitations above. The user approved this separate “verify commits” queue as part of the recommendations.

Detail selection stores a PR key and resolves current models after every sync. The original visible-key queue supports previous/next without changing filters or widening role scope. Missing/forbidden data closes the private dialog with an unavailable notice. Focus restoration uses the original trigger captured before React autofocus. No new palette, dependency, server or deployment is introduced.
